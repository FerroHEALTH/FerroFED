Where else the record is.

FerroFED is an openEHR federation gateway. A client sends it an ordinary AQL query and never learns it was federated: the gateway resolves the patient outside the query, sends standard AQL to each CDR scoped to that node's own EHR id, and merges the answers with each node's provenance. It holds no clinical data of its own.

Install and run Read about the specification

Each release ships the ferrofed binary for x86_64 and aarch64 Linux, on glibc and on musl, with SLSA provenance and SBOMs, and the image ghcr.io/ferrohealth/ferrofed for linux/amd64 and linux/arm64.

Run it

The gateway and four member CDRs, in one command

The repository's quickstart starts the published image beside four FerroEHR nodes, each with its own database and system id on one PostgreSQL server. A seed script creates synthetic patients over each node's ITS-REST API, and you send the gateway one ordinary ITS-REST query. 

git clone https://github.com/FerroHEALTH/FerroFED.git
cd FerroFED
docker compose up --wait
scripts/quickstart/seed.sh

curl -s http://127.0.0.1:8080/v1/query/aql \
  -H 'Content-Type: application/json' -d @- <<'EOF'
{"q": "SELECT c/uid/value FROM EHR e CONTAINS COMPOSITION c WHERE e/ehr_status/subject/external_ref/id/value = 'ffd-test-0001' AND e/ehr_status/subject/external_ref/namespace = 'urn:oid:2.999.1.1'"}
EOF

The answer is one ITS-REST result set with a composition from each node in its rows, and meta.federation reports all four endpoints active. Each node received a query scoped to its own EHR id, with no patient identifier in it. The patients are synthetic, resolved through a static development table, and the credentials are development values for a laptop.

To run the binary on its own, download a tarball from the latest release and verify it with gh attestation verify before you start it. The container page covers the image, the ports and the verification, and the configuration page covers the registry and the identity service. The gateway authenticates no client yet, so keep it where only trusted clients reach it; client authentication is planned for v0.0.8.

What it does

What the gateway does, release by release

FerroFED follows the openEHR Federation Working Group's Federation Tier with AQL specification, and each card answers a normative requirement there. The conformance matrix shows which points a test scores today.

In v0.0.3

Transparent to the client

/v1/query/aql takes a conformant openEHR query with no federation syntax and answers one ordinary ITS-REST result set, with the federation's additions in one metadata member that names every endpoint.

In v0.0.3

No identifier reaches a node

The patient identifier is resolved to each node's local EHR id outside AQL, through an IHE PIXm PIX Manager, and consumed at the gateway. The rewrite refuses a query that would leak it, and an outbound gate checks every request again before it leaves.

In v0.0.6

Never a silent partial answer

Every node in scope is reported with a status. When a node that was asked does not answer in its time budget, the default is to fail the query. A client that asks for flagged partial rows gets them, every missing node named.

In v0.0.6

Merged as one CDR would

ORDER BY with LIMIT, bounded OFFSET pages, DISTINCT and the aggregates are applied across nodes, and a copied version can be kept once. What cannot be exact is refused with a reason.

In v0.0.6

Directed and self-describing

A client names nodes in the AQL or in a header and can select each row's endpoint as a column. OPTIONS / says what the gateway does and which members stand behind it.

In v0.0.6

Follow-ups reach the right node

A request under /v1/ehr/{ehr_id} goes to the one node that holds that EHR: the node the client names, else the one the gateway learned, else the one it finds. Two nodes claiming one EHR id are refused, never guessed between.

In v0.0.7

Writes and definitions reach their owner

A versioned write goes only to the CDR that created the version. A template goes to the node you name, or to several on request, and stored queries live at the gateway as immutable versions it can distribute to the members.

In v0.0.7

Ready to operate

A check to run before you admit a node, a registry reload on SIGHUP, health probes, Prometheus and OpenTelemetry metrics, a stored-query store on a file, PostgreSQL or a read-only directory, and a compose file in every release that starts the gateway in front of the CDRs you already run.

In v0.0.8

Every caller verified, every node reached its own way

Each caller is authenticated at the gateway, and each node is reached with its own credential: OAuth 2.0 with DPoP, the Dutch Nuts and FAPI 2.0 grants, or mutual TLS. Patients are located through XCPD, PIXm, PDQm or the Dutch NVI, consent can be checked with Mitz first, and every IHE exchange is audited.

Where the project is

v0.0.8 is the current release. It answers one federated AQL query over many nodes with the patient resolved outside AQL, merges the rows as one CDR would, and routes reads, writes and definitions to the node that owns them. Every caller is authenticated, each node is told who is asking in a token the gateway signs, and the IHE and Dutch bindings locate the patient, check consent and audit each exchange. v0.0.9 is the conformance program. The tracker's milestones are the roadmap; every issue carries its acceptance criteria, and a release is cut when its milestone has no open issue left.
