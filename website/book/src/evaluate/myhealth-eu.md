# MyHealth@EU self-assessment

This page is FerroFED's own assessment of the gateway against the
MyHealth@EU Requirements Catalogue **v10.0.0** (W10-Operation Ready,
2026-03-06). It is not a MyHealth@EU compliance check, and FerroFED holds no
Operation Ready status: MyHealth@EU runs its own compliance checks for the
national contact points in operation, and FerroFED is not a national contact
point. The badge in the README counts the rows below and says
self-assessed; it never says compliant, certified or operation ready.

## The badges on the MyHealth@EU CI line

Beside the self-assessment, the README carries one badge per MyHealth@EU
guide FerroFED is tested against: the CI builds at `build-fhir.ehdsi.eu`,
the Patient Summary and ePrescription proofs of concept the FHIR package
registry publishes, and the imaging guide's draft build. Each label names
the guide at the exact version FerroFED pins, and each says self-tested: the counts are FerroFED's own test
runs, never a MyHealth@EU result, and no badge says certified, compliant or
conformant (`scripts/checks/myhealth-eu-ci.sh` refuses one that does).

| Badge | What it counts | Where it comes from |
|---|---|---|
| MyHealth@EU NCP API 9.1.1-ci DocumentReference search | the `DocumentReference` search parameters of the NCPeH API's server `CapabilityStatement` the document list answers, out of all of them | `conformance/myhealth-eu-search.tsv`, each row with the test that shows it |
| MyHealth@EU Core 1.0.1 (CI) | the documents FerroFED's tests write whose `Patient` is valid against `patient-myhealtheu-core` | the HL7 FHIR Validator in CI, `conformance/myhealth-eu-validation.tsv` |
| MyHealth@EU Laboratory 9.2.0 (CI) | the laboratory reports valid against `Bundle-lab-myhealtheu` | the same |
| MyHealth@EU HDR 9.2.0 (CI) | the hospital discharge reports valid against `bundle-hdr-myhealtheu` | the same |
| MyHealth@EU Vaccination 10.0.0-preview | the vaccination histories valid against `bundle-euvac-myhealtheu` | the same |
| MyHealth@EU Patient Summary 1.0.0-poc | the patient summaries valid against `bundle-eps-myhealtheu` | the same |
| MyHealth@EU ePrescription and eDispensation 1.0.0-poc | the prescriptions the map mode writes valid against `MedicationRequest-myhealtheu-epd` | the same |
| MyHealth@EU Imaging 9.1.1 (draft) | the imaging reports valid against `bundle-img-myhealtheu` | the same |

The validator lane runs HL7's FHIR Validator offline over the documents the
tests write and fails when a verdict differs from the recorded one, so a
change of any count is recorded on purpose. The gateway writes no
dispensation: one it receives reaches its member byte for byte, so the
ePrescription badge counts prescriptions alone.

Each invalid verdict names its cause in the record. A summary that carries
an allergy is invalid against the Patient Summary guide, which binds
`AllergyIntolerance.code` to the eHDSI value set `eHDSIAllergenWithExceptions`
as required, while the test documents code the substance in text alone;
transcoding to the Master Value Sets Catalogue is
[#2039](https://github.com/FerroHEALTH/FerroFED/issues/2039). The imaging
report cannot be validated against the imaging guide at all: the guide's
dependency closure names `hl7.fhir.eu.base` `2.0.0-gamma`, which no package
registry publishes, so the validator loads nothing and the report counts as
invalid, recorded as an upstream report on
[#212](https://github.com/FerroHEALTH/FerroFED/issues/212).

## What the catalogue binds

The catalogue's requirements address the national contact points for
digital health and MyHealth@EU. FerroFED is one of the national
infrastructures a contact point calls through its national connector
([A national contact point](../integrate/national-contact-point.md)), so a
requirement binds the gateway only where the contact point of the country of
affiliation relies on what the national infrastructure answers: the patient
lookup, the patient summary, the prescriptions and the dispensations it
receives, the document categories, the quality of the data, the security,
availability and monitoring of its own interfaces, the record of every
access, and what the access service serves a person from it.

Every row judges the gateway's share of one requirement, and its conclusion
names whose the rest is:

| Status | What it means |
|---|---|
| met | the gateway's share is done, and the evidence shows it |
| partly-met | part of the gateway's share is done; the conclusion names the rest and its issue |
| waits-art-15-1 | the share depends on the exchange format the Art 15(1) implementing act will fix |
| not-met | the gateway does not do its share yet; the issue tracks it where one is planned |
| not-assessed | the repository holds no page or test to judge the share by |
| not-applicable | the requirement binds the contact points, the country of treatment or MyHealth@EU, not the gateway; the conclusion names the public provision that assigns it there, or says that no text FerroFED read does |

The badge's count is the rows met out of every row but the not-applicable
ones. A row whose status the repository's own pages and tests
cannot show is never marked met.

## The source and its terms

The catalogue is privileged-access: the Xt-EHR deliverable D6.1 (section 5)
says it is available only with authorisation, and Commission Decision
2011/833/EU Art 2(2)(c) excludes such documents from its reuse grant, and
FerroFED has no grant to reuse it. This page, `conformance/myhealth-eu.tsv` and the badge therefore
carry requirement ids, section numbers, statuses and FerroFED's own
conclusions, and none of the catalogue's text. `scripts/checks/myhealth-eu.sh`
holds the mapping, this page and the badge in step, and refuses a copy of
the catalogue in the repository.

The implementing act on the exchange format (Regulation (EU) 2025/327
Art 15(1)) is not adopted. When it is, every row is checked again with the
decisions it rests on (#1425).
